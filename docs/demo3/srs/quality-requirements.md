## 5. Quality Requirements

### 5.1 Purpose

Quality requirements describe how well the system must behave while it satisfies the functional requirements. For Demo 3, the focus is on qualities that can be checked against the implemented product without inventing production-scale evidence: access control, sensitive-data handling, accessibility, token reliability, normal request responsiveness, traceability, audit integrity, and deployment repeatability.

These requirements deliberately avoid vague promises such as "instant responses" or "complete protection". Each retained requirement has a stimulus, an affected artefact, a required response, and a measurable check.

### 5.2 Quality Requirement Format

Each quality requirement is recorded with:

- **Quality attribute:** The quality being evaluated.
- **Source of stimulus:** The actor, system event, or condition that starts the scenario.
- **Stimulus:** The event the system must respond to.
- **Environment:** The operating condition for the scenario.
- **Affected artefact:** The product area being evaluated.
- **Response:** The behaviour expected from the system.
- **Response measure:** The measurable pass condition.
- **Verification approach:** The evidence expected for Demo 3.
- **Traceability:** Related functional requirements or architecture documentation.

### 5.3 Demo 3 Quality Requirement Set

| ID                  | Quality requirement                                   | Priority | Demo 3 verification focus                                                                                                                                                          |
| ------------------- | ----------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `QR-AUTH-01`        | Protected access and authorisation boundaries         | High     | Protected API routes and role-scoped user interface paths reject unauthenticated, cross-user, and cross-organisation access.                                                       |
| `QR-DATA-01`        | Sensitive-data leakage prevention                     | High     | User-visible responses, audit metadata, logs, and durable notification records avoid raw credentials, tokens, token hashes, provider credentials, and unnecessary request bodies.  |
| `QR-ACCESS-01`      | Accessible core screens                               | High     | Selected login, registration, account, and dashboard screens support keyboard access, labelled controls, readable structure, and automated accessibility checks.                   |
| `QR-RELIABILITY-01` | Reliable tokenised and notification-backed actions    | High     | Tokenised account, setup, invitation, email-change, and password-reset actions complete once and recover from supported notification delivery failures without inconsistent state. |
| `QR-PERF-01`        | Responsive standard requests                          | Medium   | Representative authenticated backend API routes meet the documented local response-time target under seeded Demo 3 data.                                                           |
| `QR-TRACE-01`       | Requirement, architecture, and evidence traceability  | Medium   | Requirement IDs, architecture mappings, tests, and manual evidence can be followed through relative links without searching unrelated files.                                       |
| `QR-AUDIT-01`       | Safe and complete audit records for sensitive actions | High     | Sensitive account, organisation, session, onboarding, and platform actions record actor, target, action, outcome, timestamp, and compact non-sensitive context.                    |
| `QR-DEPLOY-01`      | Repeatable Demo 3 deployment readiness                | Medium   | The documented deployment direction has a pending release verification procedure with explicit inputs, commands, and pass/fail rules owned by deployment foundation work.          |

### 5.4 Quality Scenarios

#### `QR-AUTH-01` Protected Access and Authorisation Boundaries

| Field                 | Scenario                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Quality attribute     | Security and access control                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Source of stimulus    | Unauthenticated user, authenticated user with the wrong role, or authenticated user from another organisation                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Stimulus              | The actor requests a protected account, organisation, training, audit, or platform administration route                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Environment           | Demo 3 application running through the normal route, controller, service, and repository boundaries                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Affected artefact     | API routes, route guards, controllers, services, session handling, and role or permission checks                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Response              | The system denies access with a safe `401`, `403`, or equivalent protected-route response and does not return protected records                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Response measure      | All protected routes and user-interface paths selected for Demo 3 verification reject unauthorised, cross-user, and cross-organisation access in the tested scenarios                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Verification approach | Backend route or integration tests for protected API paths, frontend protected-route checks where applicable, and manual verification for role-specific pages                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Traceability          | [R1](functional-requirements.md#r1-authentication-and-account-access), [R10](functional-requirements.md#r10-manage-organisation-employees), [R11](functional-requirements.md#r11-manage-organisation-administrators-and-permissions), [R12](functional-requirements.md#r12-manage-insightful-phish-platform-administrators), [R14](functional-requirements.md#r14-manage-personal-account-and-security-settings), [R15](functional-requirements.md#r15-manage-organisation-lifecycle-and-access), [R27](functional-requirements.md#r27-review-audit-and-platform-oversight-information) |

#### `QR-DATA-01` Sensitive-Data Leakage Prevention

| Field                 | Scenario                                                                                                                                                                                                                                                                                                                                                                                              |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Quality attribute     | Privacy and security                                                                                                                                                                                                                                                                                                                                                                                  |
| Source of stimulus    | User, administrator, audit reviewer, system error, or notification delivery event                                                                                                                                                                                                                                                                                                                     |
| Stimulus              | A workflow handles passwords, reset links, setup links, invitation links, email-change links, SMTP configuration, provider results, sessions, or audit metadata                                                                                                                                                                                                                                       |
| Environment           | Normal operation, validation failure, provider failure, audit review, and test failure output                                                                                                                                                                                                                                                                                                         |
| Affected artefact     | Account workflows, tokenised actions, email delivery records, audit entries, logs, API responses, and rendered notification content                                                                                                                                                                                                                                                                   |

| Response measure      | Focused tests and review checks find none of the prohibited sensitive values outside the intended delivery destination, and audit or delivery metadata remains compact and stable                                                                                                                                                                                                                     |
| Verification approach | Unit and integration assertions for safe responses, audit metadata, delivery metadata, token storage, and failure handling; manual review of logged or documented evidence                                                                                                                                                                                                                            |

| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Quality attribute     | Performance                                                                                                                                                                                                                                                                                                                                                                             |
| Source of stimulus    | Authenticated organisation administrator or reviewer exercising representative implemented backend API routes                                                                                                                                                                                                                                                                           |

### 5.5 Deferred Quality Scope

The following quality topics remain important, but they are not claimed as completed Demo 3 verification targets unless a later evidence document records a specific implemented check:

| Deferred topic                                               | Reason                                                                                                                                                                |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Large-scale load, stress, spike, endurance, and soak testing | The current repository does not define dedicated load-test tooling or production-scale data volumes.                                                                  |
| Full-stack browser E2E coverage for every major role journey | Current browser checks are useful smoke and accessibility evidence, but full-stack E2E expansion should be tracked as focused testing work.                           |
| Ethical real email simulation launch readiness               | The SRS keeps the requirement for controlled real email simulation, but Demo 3 verification should only claim implemented safeguards that are present in the product. |
| Disaster recovery and backup restore timing                  | Operational recovery objectives need environment ownership and runbook evidence outside this SRS requirement set.                                                     |
| Production monitoring service-level objectives               | Monitoring and alerting targets require the final production deployment and operations ownership to be defined.                                                       |
